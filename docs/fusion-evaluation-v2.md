# 候选排名融合实验 v2

日期：2026-11-19（洛杉矶）；报告时间戳为 UTC 2026-11-20。结论：机制上有小幅改善，但未通过预先规定的门槛，不替换默认方案，不在本批案例上继续调权重。

## 先固定设计，再观察结果

上一轮六例暴露了原始分数融合的问题：两路同时命中的片段与仅向量命中的片段存在较大分差。归一化到 0—1 没有消除分布差异。

本轮只增加一种实验方式 `candidate_rank_rrf`：先按每个候选的主题加权平均分产生排名，再分别把主题排名和原问题候选排名转换为 `61/(60+rank)`，使用原有 80/20 比例加权。没有修改主题最大值聚合、偏好权重、覆盖优先、最多五个候选、来源选择和生成规则。同分候选共用竞争排名，未命中分为零；ID 仅作最终确定性排序，不因 ID 提前获得相关性分。新路线通过 `HybridRetriever.shortlist(..., fusion='candidate_rank_rrf')` 显式调用；默认仍是 `fusion='score'`。

[协议](../evaluation/fusion_v2_protocol.json)、[语料与标签](../evaluation/fusion_v2.json)在真实调用前写定；执行器在调用前保存代码、协议、语料哈希。本轮没有参数网格搜索、额外权重尝试或失败后重跑。上一轮六例只用于提出机制假设，没有再当作本轮测试结果。

这是一组前瞻性合成开发验证：语料由同一个开发助手编写，并受已知问题影响，不是独立人工标注的盲测或真实用户留出集。结果一旦观察，该批案例即成为开发数据，未来改动需要新的留出验证。

## 固定的材料与评价

18 个虚构候选，每个一个短来源；8 个问题，涵盖日出前/晚餐后、十五分钟/六小时、周末/工作日睡眠、两种多主题远程工作场景。查询与来源均为英文，以减少上一轮中英文混杂；本轮不验证中文能力。

所有候选结构化条件相同，所有方法最多选五个候选/来源，不通过增加上下文数量获得优势。场景相关性标签包括明确的使用语境及观察局限，不等于一般主题相关性，也不表示所有要求都已满足。模型没有生成解释。

此外记录泛化主题风险：即使“网络不稳定”没有具体时间，它也可能值得让用户知道。因此同时观察场景风险召回、泛化主题风险召回，以及新方式挤掉的风险，防止只追求细节指标而隐藏一般风险。

预设门槛：两个主要宏平均指标都提高、至少三个问题的场景召回提高、没有挤掉原方案已找到的风险。即便全部通过，也不凭这一小批助手编写的案例自动切换生产默认。

## 逐例检查

| 问题 | 旧分数融合场景召回 | 新排名融合场景召回 | 主要变化 |
| --- | ---: | ---: | --- |
| 日出前会议 | 0% | 0% | 未引入日出前的相关资料 |
| 晚餐后会议 | 66.7% | 66.7% | 用网络稳定经历替换了晚间噪声但网络正常的经历，相关数量不变 |
| 十五分钟会议 | 0% | 33.3% | 引入短时通话掉线风险 |
| 六小时培训 | 0% | 0% | 仍未引入长时使用或长时断线证据 |
| 周末睡眠 | 40% | 40% | 前五名集合不变 |
| 工作日睡眠 | 66.7% | 66.7% | 前五名集合不变 |
| 工作日日出前会议＋安静 | 0% | 20% | 引入日出前噪声风险，但挤掉了周末晚间噪声风险 |
| 周末晚餐后会议＋安静 | 40% | 40% | 引入一条泛化安静风险，但未增加该场景相关数量 |

两个问题提高，六个问题的场景召回持平；没有场景召回退步。但“无挤掉风险”门槛没有通过：工作日场景换出了周末噪声风险。这个替换未必对真实用户不合理，说明预设门槛比较保守；仍按事前规则报告未通过，不事后改门槛宣布成功。平均风险召回上升也不能掩盖具体来源被换出的事实。

新方法仍落后于更简单的纯主题向量对照，不能因为战胜旧混合就宣布架构更优。原问题单独检索的场景召回较高，但泛化主题风险召回更低，也不能仅凭场景分数替换所有路线。

## 机制解释与未解决问题

转成候选排名后，双命中造成的数值差距不再直接主导最终融合，部分原问题相关来源终于进入前五名，支持这一机制方向值得研究。但权重仍为 80/20，原有主题排名偏差也仍存在：例如附近会议中心的描述在多主题结果中仍然排得很高。排名融合不能自行判断“谈到的是否是房源自身”。

本批候选都少于每路 40 条检索上限，所有候选都被每个主题的向量路线返回，所以主题覆盖数量在各问题内一致。虽然保留了覆盖优先规则，实验没有证明它能在更大候选池中可靠工作。

适合下一轮的新假设是：在融合之外或之前判断资料是否真的描述候选自身的相关属性/经历，并保留正面与负面方向，观察能否减少会议中心、广告设施词等干扰。需要另定有限实验和新案例；本轮不在已看过的数据上继续优化，也不宣称提高权重必然有效。

## 资源与复现

```sh
.venv/bin/python evaluate_fusion.py
```

该命令会发起有限的真实嵌入请求。协议上限为 12 次、每批最多九条、每文本 500 字符、响应 4 MiB、进程峰值 RSS 256 MiB、总时长 180 秒。执行器每 0.2 秒用信号检查进程内存和时限，超限抛出异常、清理临时数据并保存停止状态；不自动重试或提高上限。所有调用串行，无生成模型调用、并行代理或新服务。

本次实际：10 次嵌入请求、542 个输入 token、8.74 秒、峰值 RSS 51.72 MiB。主题查询命中已有缓存；12 次上限也允许两个主题冷缓存。临时候选和导入记录在 finally 中清理，生产表计数前后保持一致。

新排名方式和同分/缺失处理加入回归测试；63 项测试全部通过，包括五项真实 PostgreSQL 集成测试。测试本身没有付费调用，峰值约 52.17 MiB。
