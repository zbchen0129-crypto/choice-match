# 检索开发评估 v1

2026-11-11 实际运行 PostgreSQL + pgvector 和 `text-embedding-3-small`。本轮没有调用生成模型，也没有修改检索算法或依据结果调参。

## 数据与协议

[冻结语料](../evaluation/retrieval_v1.json)包含 30 条新编写的虚构文本，按六个候选组织，每个候选五个来源。五个主题各有四条相关来源（两条支持、两条风险），另有十条干扰来源。相关性指该房源的主题证据；负面经历同样属于相关证据。广告附近商店出现相同关键词，不算该房源的证据。

标签由开发助手编写并在首次检索前固定，不是独立人工标注，不是外部测试集。语料刻意包含同义表达、中文风险与词义干扰，规模小、分布人为设计，不能代表真实数据总体质量。看到结果后，此语料应作为开发回归集；后续效果结论需要另建未参与调参的测试集。

语料 SHA-256：`8fe3ce9f85a2f3f00580c46b06d9e27d3962153928d59086f95416bda2d4bcbd`。

三种检索使用同一批资料、生产中的固定主题查询与每通道最多 40 个片段的召回上限。融合后按来源去重，统一截取前五个来源。Precision@5 分母固定为 5，即使实际不足五个；Recall@5 分母是该主题四条相关来源；Risk recall@5 分母为两条风险来源。下表是五个主题的宏平均。此语料每个来源都只有一个片段，尚未评估长文分块。

## 实测结果

| 检索方式 | Precision@5 | Recall@5 | 风险 Recall@5 |
| --- | ---: | ---: | ---: |
| 关键词 | 40% | 50% | 50% |
| 向量 | 76% | 95% | 90% |
| 当前混合 RRF | 64% | 80% | 70% |

[完整原始报告](../evaluation/result-20261111T221144-1ff573.json)保存每个主题的来源排名、漏掉的风险、查询、代码哈希和模型名称。这里的 95% 是本次合成语料的检索召回率，不是推荐准确率。

关键词检索漏掉不同措辞和中文同义表达。混合融合给予同时命中两路的资料更高分，因此也可能抬高关键词干扰：例如安静主题中耳机商店文案排到第二，中文凌晨练鼓风险掉出前五。向量检索也有缺陷：停车主题仍将异地车库和戏剧名称排在中文找车位困难经历之前。

仅含十条无关来源的候选池中，三种方法在五个主题上都返回了资料，非空返回率均为 100%。这测量的是检索不拒答行为，不是模型产生错误断言的比例。当前向量路径没有相关性门槛，返回最近邻并不意味着资料真的相关。

## 短名单检查

偏好为安静与视频会议时，当前混合短名单依次选出 C、A、F、E、D，漏掉具有相关证据的 B；E 和 F 只有干扰来源。候选 C 和 D 的四条已标注风险均进入后续抽取上下文，但每个候选仅五条来源，小于单主题六条的召回上限，所以不能据此证明大规模上下文截断下风险不会丢失。

相关性排序并非适合程度排序：风险材料被召回本身是正确行为。真正的问题是无关来源也会增加 `topics_retrieved` 覆盖，影响候选入选。生成阶段是否能正确拒绝这些材料，本轮未测量。

## 复现与隔离

```sh
.venv/bin/python local_db.py start
.venv/bin/python evaluate_hybrid.py
```

脚本从本地 `.env` 读取配置，发送这 30 条虚构文本和未缓存的主题查询到嵌入接口，可能产生费用。临时数据集使用唯一 ID；只对自己的片段写入向量，结束或异常时删除自己的候选和导入记录，保留可复用的主题查询缓存。每次成功运行保存一个新的报告，不覆盖旧结果。

本次索引消耗 617 个输入 token，未缓存查询消耗 40 个输入 token；缓存命中不产生新嵌入请求。重跑会重新嵌入临时资料。清理后数据库仍为 152 个候选、158 个来源/片段，评估候选残留数为零。45 项自动测试通过，其中五项是真实 PostgreSQL 集成测试；新增两项验证来源去重和指标分母。

## 下一步

先在开发集上建立来源相关性判断，允许明确返回证据不足，并验证它保留正面与负面证据。候选覆盖应依据相关来源，而非仅依据最近邻返回。随后用新冻结语料比较修正前后结果，补充长来源、跨候选重复、更多中英文表达及无相关证据场景；模型抽取和解释的语义支持需要单独评估。没有证据支持直接宣布某种检索方法普遍最优。
