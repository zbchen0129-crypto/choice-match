# ChoiceMatch 开发计划

项目面向 AI 应用及软件工程求职。第一个完整场景是租房推荐，第二个验证场景是短期住宿；项目不以替用户找房或实时预订为目标。

## 产品边界

演示城市选择芝加哥，承接学校时期 Airbnb 项目的故事线。首轮使用手工编写且明确标注的虚构候选和证据，验证约束处理；随后验证可用数据来源与授权，再添加真实数据适配器。Zillow 和 Redfin 是灵感来源，不代表已建立数据接入。

租房 MVP 支持租金及已知月费、卧室数、宠物规则、停车、洗衣条件、办公及噪声证据。未知不能作为满足条件；缺失强制月费时，只显示费用下界。押金和一次性费用后续独立显示，不混入月租。当前不支持实时可租、通勤路线、交易、治安判断或持续抓取。

## 通用核心和场景模块

- 核心对象：Candidate、Attribute、Source、Evidence、Requirement、Comparison。
- Attribute 保存值、来源和记录时间；未提供的值为 null。多个冲突来源应保留，不能无声覆盖。
- Source 保存原文、来源类型和日期；发布日与采集日应分别建模。
- Evidence 保存候选 ID、主题、原文片段、来源 ID、正负方向、适用条件及日期。
- 场景模块定义字段、单位、硬条件运算和领域计算。租房模块处理月度费用；汽车模块将来需要单独处理车辆车况。
- 用户需求包含硬条件、偏好权重、相关主题和适用条件。首版以结构化输入验证核心，再接自然语言解析与可编辑需求卡。

## 目标架构

离线：导入原始资料 → 标准化字段 → 模型抽取证据 → 校验原文及来源 → 保存结构化记录与检索索引。

在线：需求解析 → 用户可修正 → 数据库硬条件筛选 → 按候选及主题检索证据 → 汇集正负证据 → 排序 → 模型生成带引用解释 → 校验引用。

硬条件使用满足、违反、未知三态。违反者排除，未知者独立列为待核实。检索不能只找正面证据；相关不代表有利。适用条件必须进入判断，历史信息保留日期，不直接当作当前事实。

通用层不硬编码城市、网站或房源字段。早期使用 JSON 和 Python 标准库验证契约；持久化、关键词及向量检索、API 和前端在对应阶段加入并记录选型理由。当前规则分用于验证流程，未经评估不能称为最优排序或概率。

## 评估设计

先构建人工标注的租房案例，覆盖完整费用、缺失费用、硬条件违反、资料矛盾、历史噪声、需求变化及无合适候选。规模在标注试跑后确定，不把虚构数据上的表现外推到真实场景。

将抽取、检索和推荐分开测量：字段准确性及缺失识别；证据检索 recall@k；引用原文匹配与语义支持；硬条件违规率；冲突及时间条件识别；需求覆盖；人工成对偏好比较。排序评估使用冻结的场景与人工判断，并记录评审分歧。

基线包括纯结构化筛选、相同资料加完整提示词直接交给模型、完整管线。固定模型与输入，区分索引预处理成本和在线查询成本；保留测试集，不用测试结果反复调参。代码单元测试通过不代表模型或推荐效果达标。
