# ADR 001：保留用户原话的独立向量检索路线

状态：第一版已实现；真实语义质量对照尚未运行。记录依据：2026-11-19 会话及此前检索评估。用途：保留设计推演、工程取舍和面试叙事，区分已实现行为与尚未证实的效果。

## 问题从哪里来

原实现把自然语言解析为预算、卧室、养猫及固定偏好主题。检索只使用固定主题查询，因此“白天十分钟会议”和“凌晨连续四小时跨国会议”可能产生同一个 video_calls 查询。原话也没有传给抽取、解释阶段。

此前 30 条合成开发语料中，关键词、向量、混合 Recall@5 分别为 50%、95%、80%；混合方式会抬高关键词干扰。该结果不是推荐准确率，也不能证明新路线有效。见 ../retrieval-evaluation.md。

## 讨论路径与取舍

1. 用户提出保留主题检索，增加完整原问题向量检索，让时间、时长等个人语境影响召回。
2. 最初讨论将凌晨、四小时、跨国等条件进一步结构化，并记录条件覆盖。用户指出任意问题细节各异，字段扩展复杂且难控制。第一版采纳用户方案：保留原话字符串，不增加细节 schema；已有硬筛选字段继续保留。
3. 讨论发现，原问题与某片段的相似度是全局信号。若在每个主题里重复添加，就会随主题数和主题权重被反复累加，也可能被误当成多个主题的证据覆盖。
4. 决定将原问题作为独立路线，只在候选总分里加入一次。主题覆盖仍然只来自原有主题检索。相关性高可以表示负面风险高度相关，不能理解成推荐适合度高。
5. 用户确认原算法每个候选、每个主题取最高片段分；保留这一机制，避免资料多者靠累加占优势。主题汇总从加权和改成加权平均，避免用户整体放大主题权重时无意改变原问题路线占比。
6. 用户确认第一版仍按“主题命中数优先，再比较融合总分，再按 ID”排序。其缺点也明确保留：覆盖少但高度贴合原话的候选，仍可能被覆盖多的候选压住。第一轮不同时更改此排序规则，以减少实验变量。
7. 举例讨论中的 90、85、60、95 和 80/20 是解释用数字，不是实测相似度。实现采用有明确定义的 RRF 归一化，20% 仅为待评估的实验起点。

## 实现公式

对候选 c、主题 t，取该候选片段的最高两路 RRF 分：

    R(c,t) = max_chunk(1/(60+lexical_rank) + 1/(60+semantic_rank))
    T(c,t) = R(c,t) / (2/61)
    T(c)   = sum(weight(t) * T(c,t)) / sum(weight(t))

未命中的路线贡献零；未命中的主题在平均分中贡献零。2/61 是两路均排名第一时的理论最大值，不代表概率校准。

原问题在整个硬筛选候选池中检索一次：

    U(c) = max_chunk(1/(60+original_rank)) / (1/61)
    S(c) = (1-alpha) * T(c) + alpha * U(c)

默认 alpha=0.2。使用排名而非原始余弦距离参与融合；距离保存在调试 trace 中。距离发生变化但名次未变，融合贡献可以不变。原问题没有命中的候选 U=0。

按主题命中数量降序、S 降序、ID 升序排序，最多选五个候选。该分数用于深入分析顺序；最终推荐仍由抽取证据和原有规则评分产生。

空原问题或 query_weight=0 不运行新路线；空原问题下的归一化只引入候选共同缩放，保留旧短名单顺序。没有任何偏好主题但有原问题时，仅使用原问题分；两者皆空时按 ID 排序。

## 来源选择与原话传递

- 页面在 /api/rag 顶层发送 original_query；不加入硬条件 schema。
- 原问题向量在当前 retriever 实例中缓存；同一请求内全局检索及入选候选局部检索复用，不写入持久化 query_embeddings，避免持续存储任意用户原话。
- 全局原问题检索最多 40 条；每个入选候选另取最多六条原问题命中。它们与该候选各主题的来源 ID 合并去重，确保原问题新召回的风险可进入上下文。
- 两路主题检索每主题每通道局部上限六条，五个主题加原问题最多涉及 66 个来源 ID/候选；当前抽取还受 60,000 字符的来源表示长度上限约束，超限报错，不静默截掉风险。
- 原话和确认后的结构化条件均传给抽取与解释；提示词声明结构化条件优先、原话是上下文、通用主题证据不保证覆盖具体时间/时长。不增加模型调用次数，但会增加少量输入文本。
- 原话编辑使旧结果失效；切换预设模式或明确移除未处理限制时清空原话，避免重新引入放弃的限制。
- 手动修改结构化字段后仍保留原话：硬筛选以当前字段为准，模型提示也如此；旧原话仍可能影响软检索，是已知局限，用户可同步编辑原话。
- 数据库 RAG 路径不再额外创建并填充未使用的 SQLite 内存索引。显式 JSON/旧 CLI 仍为旧关键词路径，不声称已接入新向量路线。

## 边界与资源限制

原问题最多 4,000 字符，与嵌入客户端单文本上限一致；超限或非字符串拒绝，不静默截断。候选池最多 1,000 个，最终最多五个；超限拒绝。空候选池不调用嵌入。只有新路线启用且有候选时，增加至多一次原问题嵌入请求；检索顺序执行，不新增服务或本地模型。

这次验证使用假嵌入和假生成模型，真实 PostgreSQL 只验证存取和隔离，没有付费模型请求。测试进程限制 256 MiB 峰值 RSS、60 秒，超限直接停止，不重试或提高预算。

## 已验证与未验证

本轮最终运行 55 项测试全部通过（包含五项真实 PostgreSQL 集成测试，未跳过），测试进程峰值 RSS 48.02 MiB；记录见 [实现验证结果](../../evaluation/original-query-implementation-validation.json)。页面传参代码已修改，尚未另做浏览器端到端实测。

自动回归覆盖：每主题取最大值、用户权重平均、权重同比放大不放大原问题信号、新风险来源保留、原问题不增加主题覆盖、覆盖优先阻止跨层逆序、空查询及关闭路线回退、原话传给两阶段模型、非法输入在调用前拒绝、SQL 候选范围隔离、向量在一次请求内复用且不持久化原话。

尚未验证：真实嵌入是否把凌晨/长时场景排得更合理、原问题是否被预算等字段稀释、20% 是否适宜、增加的上下文是否提高抽取和解释质量、真实用户数据上的泛化。没有宣称效果提升。

后续对照应同时保留当前混合、纯主题向量、混合加原问题三种配置；固定最终候选名额和上下文预算，记录新增有效证据、被挤出的风险、无关材料及短名单漏选。逐例串行执行并监控内存。旧语料作回归，新冻结的成对问题用于检验细节变化；调参后另用未参与调参的案例复验。

## 面试可讲述的版本

“我发现固定主题检索会压缩用户语境。设计时考虑过把所有场景细节结构化，但为了控制复杂度，最终保留用户原话，增加一条独立向量路线。我们识别出把全局信号塞进每个主题会重复计分，因此采用归一化主题加权平均与一次全局信号融合，并保持原来的主题覆盖优先规则作为对照。工程上补齐原话从界面到抽取、解释的传递，验证候选隔离和向量复用，同时记录覆盖优先和语义判断的局限。实现及回归测试已完成，真实质量提升仍需实验验证。”


## 后续实验证据：2026-11-19

[六个场景对照](../original-query-evaluation.md)已经完成，7 次真实嵌入调用、435 输入 token、峰值 51.09 MiB。当前混合和混合加 20% 原问题的场景 Recall@5 同为 22.2%；原问题单独路线为 63.1%（仅诊断，不是生产提升）。当前权重未改动。

这次推翻了“给原问题 20% 就足以改善短名单”的未经验证预期。两路 RRF 的双命中奖励在归一化后仍造成较大分差，原问题信号难以弥补。单主题下所有候选覆盖相同，所以本次主要问题是分数融合，而非覆盖数优先。另发现完整问题的硬字段可能稀释细节，中文/英文表达也存在混杂。

面试故事现在可继续讲：“我保留了没有提升的实验结果，定位到归一化不等于校准、检索新信号不等于最终短名单改善；下一轮将独立比较融合方式，而不会把单路指标宣传成生产指标。”

浏览器交互与请求传递已用测试替身验证，真实生成端到端质量仍未验证。最新自动回归为 59 项全部通过。


## 第二轮：候选排名融合，仍不替换默认

用户明确要求避免过拟合。采用一种机制变化：候选主题平均分先转排名，再与原问题候选排名按原有 80/20 融合；不扫描权重，保留主题覆盖优先。新语料、标签和采用门槛在调用前冻结。

18 条新英文来源、八个问题实测：新排名融合场景 Recall@5 为 33.3%，旧分数融合为 26.7%；风险召回为 50% 对 33.3%。仅两个问题的场景召回提高，且挤出了一条泛化风险；纯主题向量场景召回仍更高，为 40%。按事前规则判定未通过，不推广为默认，不在新案例上继续调参。

这是助手编写的前瞻性开发检查，不是独立人工留出测试。完整材料和失败案例均保留，见 [第二轮实验](../fusion-evaluation-v2.md)。这段决策体现“先提出机制假设、事前规定判断标准、发现局部提升仍不夸大为全面收益”。


## 后续交互：固定五档离线实验面板

用户提出让使用者选择主题与原话细节侧重。决定先提供独立开发实验页面，避免将未验证权重称为可靠的生产模式。使用已观察八例的完整检索快照比较 0/20/50/80/100%，不重新调用嵌入或生成模型、不增加样本、不追加权重网格搜索。

开发集上 50% 的场景召回为 56.7%，高于 20% 的 33.3%，但一般主题风险召回由 49.7% 降至 45.1%；80% 也未持续改善。因此不选择最佳档位、不改变生产默认。页面同时呈现收益、丢失风险、具体原文和可导出的实验记录。这是可复现的取舍演示，不是独立效果证明。见 [实验室记录](../weight-lab.md)。

## 2026-11-20：先验证来源相关性，不继续追逐权重

离线权重面板之后，增加独立的来源相关性实验：具体证据/仅提及/无关/不确定，支持与风险分开保留，并标注条件覆盖。用户原话仍完整传入，不添加任意细节的请求 schema。覆盖不全不等于无关；检索相关也不等于房源适合。

首次有限实测在第二组的逐字引用校验处停止；保留失败，不重试覆盖结果。补充失败前输出审计，未接入生产。此处的工程教训是：语义判断与输出契约必须分开审计，标签正确的单组结果不能证明整条链路可靠。[实验记录](../source-relevance-experiment.md)。

### 短来源原文绑定与语义边界

新增仅返回来源 ID 与判断、由程序附加完整短来源的实验模式，消除模型重抄引用的环节。旧案例诊断超时，不能猜测旧引用错误的具体原因。新冻结 v2 记录了全部四批原始返回，第四批因 evidence/none/none 停止；风险保留 5/6，未进入正式过滤链路。

新发现：支持“全时段安静”通常需要整个时段的观察，反驳它只需时段内一个噪声反例。观察覆盖与反例相关性不能混用一个含糊标签。保留原有冻结标签与失败，不通过事后重标美化结果。下一步先改进定义及审核方式，再开展新验证。[完整记录](../source-relevance-v2.md)。

## 2026-11-23：风险筛查优先，避免过度证明需求覆盖

用户指出推荐系统应先否定筛查雷点，再按符合情况推荐；不需要证明每个细节完全满足。接受此方向，但区分明确不可接受的冲突和一般风险，未知不算支持。正式规则输出支持/风险/缺失摘要，新增独立人工审核排除接口；模型标签不能自行触发淘汰，原话与来源变化使审核失效。保留当前排序与权重。本轮只实现后端规则和离线演示，下一步接入页面交互。[实现与局限](../risk-first-recommendation.md)。

页面已落实“用户看依据后排除”：将用户个人决定与模型判断/事实认证分开，选择引用原文并说明理由，允许撤销；需求与来源指纹使陈旧决定失效。本轮没有增加付费模型调用或改变融合权重。当前边界是用户控制的筛查，不宣传自动语义排除已经可靠。
